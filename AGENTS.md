# AGENTS.md — Coding Agent Operating Manual

> Give this file to your coding agent and check that it is using these instructions. Keep the stack, commands, and ground rules current.

## 1. Project Overview
- **What this repo builds:** Steelman, a shared argument document for understanding the strongest case for each option. Build 1 is a static Product Page plus a supplied browser-local card prototype. From Build 2, the real product is built in `app/`, milestone by milestone (`plans/build-plan.md`).
- **Primary user & core workflow:** Pod 6 classmates are the initial reachable testers. Read the two cases, compare wording, inspect evidence, and suggest a better version. The class PRD is in `docs/index.html`; the original long-term vision is preserved in `docs/reference/steelman-prd-v0.4.md`.
- **Tech stack:** Buildless HTML, CSS, and JavaScript. GitHub Pages serves `main:/docs`. No backend, private keys, package installation, or live AI calls. Usage analytics and session replay go to PostHog (US cloud) through `docs/analytics.js`, with a first-visit opt-out notice and Global Privacy Control / Do Not Track honored (see `docs/privacy.html`; keep that page true to what the site collects), using PostHog's public project key; the prototype's frame posts action names to its page, which forwards them. That describes `docs/`, which stays as it is.
- **Tech stack (the app, from Build 2):** TypeScript end to end, in `app/`: a React + Vite web app, a Fastify API, Postgres 17 through Kysely (plain SQL migrations), and Better Auth for Google and email-link sign-in (no passwords). Hosted on GCP (Cloud Run, Cloud SQL, Secret Manager) in separate staging and production projects, with infrastructure as Terraform in `infra/`. Email goes through Resend; PostHog stays. The design is in `plans/architecture.md`, its decision records in `plans/decisions/`, and the phases in `plans/build-plan.md`. Follow them, and propose a change to them before departing from them.
- **Feature audit:** `plans/features.csv` lists every feature with its MVP tier, development complexity, and design readiness (1–5; design-ready means 4). It is the record; `plans/feature-audit.xlsx` is generated from it by `python3 scripts/build-feature-audit.py` (needs `openpyxl`) and is never edited by hand.
- **Visual identity:** Design tokens live in `docs/design/tokens.css`; the specimen is `docs/design/index.html` and the identity brief is `docs/design/README.md`. After changing tokens or the prototype source, run `python3 scripts/sync-prototype.py`. The canvas contour tile comes from `python3 scripts/make-contours.py`.

## 2. Commands
- **Install dependencies:** `docs/` needs none: a modern browser is sufficient, and the prototype loads fonts and icons from public CDNs. The app needs Node 22 LTS and Docker, then `npm install` in `app/`.
- **Run locally:** `python3 -m http.server 8000 --bind 127.0.0.1 --directory docs`, then open `http://127.0.0.1:8000/` or `/prototype/`. Alternatively, open `docs/prototype/index.html` directly. The app: `docker compose up -d db`, then `npm run dev` in `app/`, and open `http://localhost:5173`. Locally, sign-in links print to the terminal instead of being emailed.
- **Verify:** in `app/`, `npm run check` runs everything a pull request must pass: types, lint, the rules, the database invariants, the API, the simulation, and the browser tests. It starts its own database and needs no network or accounts (`plans/architecture.md` §8). `npm run test:soak` is the slow run (30 scripted voters for 5 minutes) that also runs nightly. Then `git diff --check`. For `docs/` and the prototype, follow `tests/build-1-manual.md`. Use browser checks for actual behavior; do not claim user research from agent testing.
- **Run model evals:** Not applicable until milestone M3c (the AI evidence check); no model runs before then.
- **Database migrations:** `npm run db:migrate` in `app/` applies them locally; CI applies them to staging and production.
- **Rebuild the feature audit:** `python3 scripts/build-feature-audit.py` (requires `pip install openpyxl`; only this script needs it).

## 3. Non-Negotiable Engineering Rules
1. **Work from the approved plan:** An item in a milestone's backlog (`plans/build-plan.md`) is already approved: build it without asking, one item per pull request, then take the next. For anything else that touches multiple files, propose a brief plan and wait for approval.
2. **Small batches:** Make small, focused changes that can be reviewed and explained by a human in a single Pull Request.
3. **Explainability:** Avoid unnecessary abstractions or dependencies. Help the human builder understand the main components, what changed, why it matters, what could break, and how it was checked.
4. **Verify changes:** In `app/`, write the item's acceptance tests first and see them fail, then build until `npm run check` passes. Name each test with the feature IDs it covers. For a reproducible logic bug, use a failing test to demonstrate the fix. Record manual checks and known limitations; follow the selected Build 4 evaluation track.
5. **Zero secrets in code:** Never hardcode API keys, tokens, or credentials. Always read from environment variables (`.env`) and update `.env.example` when new variables are needed.
6. **Keep the feature audit current:** When a change adds a feature, changes what one does, or closes a design gap, update its row in `plans/features.csv` in the same PR: `status`, `readiness`, `design_gaps`, `changed` (today's date), and `evidence` (the dated `tests/build-1-manual.md` entry). Give a new feature the next free ID in its area; never renumber. Change `tier` or `complexity` only with the human's agreement. Then run `python3 scripts/build-feature-audit.py`, and name the feature IDs in the test-log entry's heading.
7. **Migrations only move forward:** Never edit a migration that has run in staging; add a new one. Every migration must work with the code already running (add, then switch, then remove).
8. **Stop when looping:** If a fix fails twice in a row, stop, summarize what failed, and ask the human before trying a third approach.
9. **Never weaken a check to pass it:** Don't edit, skip, delete, or retry an existing test, replace a saved screenshot, or loosen the policy table to make a change pass. If an old test is wrong, say so in the pull request and leave the decision to the human. Adding tests is always fine.
10. **Stop and ask:** Leave a note on the pull request or an issue, and move to another unblocked item, when a change would: depart from `plans/architecture.md` or a decision record; add a run-time package; drop or rewrite existing data; let a role do more than before; change what is collected about people; cost money or need an account; or release to production. The full list, and what stays with the human, is in `plans/architecture.md` §8.
11. **Merging:** Don't merge your own pull request unless the human has turned that on (`plans/architecture.md`, Q18). Until then, open it, and start the next item on a branch that builds on it.
